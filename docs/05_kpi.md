# 5. Оцінка результативності

Показники взято з лекційного матеріалу «Організація, управління та оцінювання ефективності командної взаємодії в процесі проектування баз і сховищ даних» (таблиця 1) і перекладено на масштаб навчального проєкту. У матеріалі три рівні оцінювання — на них і спираємось.

> Шаблон. Значення заповнює команда наприкінці спринту. Оцінюємо об'єктивно — не хвалимо й не «топимо».

## Як метрики з лекції виглядають у нашій лабораторній

У нас немає CI/CD, ETL-конвеєрів і промислового середовища, тому для кожної метрики взято найближчий показник, який реально порахувати.

| Рівень оцінювання | Метрика з лекції | Що рахуємо в ЛР5 | Звідки дані |
|---|---|---|---|
| Продуктивний внесок команди | частота розгортання міграцій | кількість змін DDL, злитих у `main` за спринт | історія комітів |
| | час проходження задачі від ідеї до експлуатації | днів від створення Issue до його закриття | дошка проєкту |
| | частка релізів без помилок | частка Pull Request-ів, прийнятих без доопрацювань | коментарі в PR |
| Якість архітектурних артефактів | кількість критичних зауважень на рецензуванні | кількість зауважень у журналі `04_review_checklist.md` | журнал зауважень |
| | рівень покриття тестами цілісності | пройдені тести з `sql/tests/03_integrity_checks.sql` / усі тести | результат запуску скрипту |
| | відсоток актуальності документації | таблиці й поля, що збігаються в DDL, діаграмі та `02_schema_design.md` / усі | звірка вручну |
| Експлуатаційна ефективність | середній час виконання аналітичних запитів | час кожного з 5 запитів (`\timing on` у psql) | запуск `analytics.sql` |
| | стабільність ETL-конвеєрів | скрипт наповнення виконується без помилок із першого разу (так / ні) | запуск `02_sample_data.sql` |
| | відсутність деградації індексів | запити використовують індекси зовнішніх ключів (перевірка через `EXPLAIN`) | план запиту |
